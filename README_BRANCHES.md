# أساس نظام الفروع (Branch Foundation)

هذه حزمة تحضيرية فقط: تجهّز البنية التحتية بحيث لو طلب العميل "فروع" بعد أشهر، تصير إضافة فرع
عملية سهلة (شاشة + فلترة) بدل إعادة هيكلة المشروع وتعديل بيانات موجودة بأثر رجعي.

**لا تغيّر أي شيء في تجربة المتجر الحالية.** المتجر يستمر يشتغل كفرع واحد بالضبط كما هو الآن.

---

## 1) ليش هذا التصميم بالذات؟

بدل نظام Multi-tenant كامل (قاعدة بيانات/schema منفصل لكل فرع - معقّد وغير مبرر لمتجر واحد الآن)،
اعتمدنا مبدأ **"فرع كبُعد إضافي" (dimension)** وليس "نظام منفصل":

- المنتجات، الفئات، العملاء، بوابات الدفع، الصلاحيات: **تبقى مشتركة بين كل الفروع**.
- المخزون/السعر لكل فرع، الطلبات، الموظفين: **تُربط بفرع عبر عمود `branch_id`**.
- الاسم والعنوان (الحقول التي تحتاج لغات متعددة) تُخزَّن عبر **astrotomic/laravel-translatable**
  في جدول منفصل `branch_translations` بدل أعمدة `name_ar`/`name_en` - هذا يسهّل إضافة لغة ثالثة
  مستقبلاً (صف جديد بدل عمود جديد بالـ schema)، ويوحّد أسلوب الترجمة مع بقية مشروعك لو مستخدمها
  أصلاً بجداول أخرى.
- كل الأعمدة/الجداول الجديدة **Nullable/اختيارية**، فلا يوجد أي كسر للنظام الحالي.

هذا يعني: لو ما طلب العميل فروع أبداً، الكود الإضافي هذا **بدون أي أثر ملموس** على أداء أو سلوك
المتجر. ولو طلبها، أنت أضفت صف بجدول `branches` + شاشة اختيار، وليس تعديل بيانات إنتاج حقيقية.

---

## 2) خطوات التركيب (الآن)

1. ثبّت الحزمة إن لم تكن مثبّتة أصلاً بمشروعك:
   ```
   composer require astrotomic/laravel-translatable
   ```

2. انسخ الملفات فوق مشروعك (نفس المسارات: `app/`, `config/`, `database/`).
   - لو عندك `config/translatable.php` منشور مسبقاً (لأنك تستخدم الحزمة بجداول ثانية)، **لا تستبدله**
     - فقط تأكد أن `locales` فيه يحتوي `ar` و`en`.

3. شغّل الميجريشن:
   ```
   php artisan migrate
   ```
   الميجريشنز **دفاعية بالكامل** (تتحقق من وجود الجدول/العمود قبل أي تعديل)، فهي آمنة تماماً
   حتى لو اختلفت تفاصيل مخطط قاعدة بياناتك عن الافتراضات هنا.

   > ملاحظة: ميجريشن `add_branch_id_to_staff_tables` تفحص أسماء `employees`/`admins`/`staff`
   > تلقائياً. لو اسم جدول الموظفين عندك مختلف، عدّل مصفوفة `$candidateTables` بالملف قبل التشغيل.

4. شغّل السيدر (يُنشئ "الفرع الرئيسي" بترجمتين ar/en، ويملأ `branch_id` لكل الطلبات/الموظفين
   الموجودين مسبقاً):
   ```
   php artisan db:seed --class=BranchSeeder
   ```

5. لا حاجة لأي تعديل آخر الآن. لا شاشات جديدة، لا تغيير بمسار الطلب الحالي.

### أمثلة استخدام سريعة (لما تحتاجها لاحقاً بشاشة الأدمن)
```php
$branch = Branch::main()->first();

$branch->name;                      // الاسم بلغة التطبيق الحالية app()->getLocale()
$branch->translate('en')->name;     // الاسم بالإنجليزي صراحة
$branch->translate('ar')->address;  // العنوان بالعربي صراحة

// إنشاء/تعديل فرع بترجمتين دفعة واحدة:
$branch = Branch::create(['is_active' => true, 'phone' => '05xxxxxxxx']);
$branch->translateOrNew('ar')->fill(['name' => 'فرع رام الله', 'address' => '...']);
$branch->translateOrNew('en')->fill(['name' => 'Ramallah Branch', 'address' => '...']);
$branch->save();
```

## 3) خارطة الطريق - لما يُطلب فعلياً نظام فروع

عندها فقط، هذه هي الخطوات (بالترتيب) ولن تحتاج تلمس الميجريشنز أو البيانات القديمة:

1. **شاشة إدارة الفروع بالأدمن** (CRUD بسيط على جدول `branches` الموجود أصلاً).
2. **ربط كل موظف بفرعه** من شاشة الموظفين (العمود `branch_id` جاهز أصلاً).
3. **تفعيل `BelongsToBranch` trait** على موديل `Order` (وأي موديل ثاني يلزم) بسطر واحد.
4. **تحديث `BranchContext::current()`** ليقرأ الفرع الفعلي بدل "دايماً الرئيسي" - حسب الحالة:
   - متجر ويب: صفحة اختيار فرع تُخزَّن بالـ session، مع اقتراح أقرب فرع عبر `lat/lng`.
   - تطبيق موبايل: Header (`X-Branch-Id`) يرسله التطبيق بعد اختيار المستخدم.
   - لوحة التحكم: `auth()->user()->branch_id` لفلترة الطلبات تلقائياً لكل موظف.

   **هذا هو التعديل الوحيد المركزي.** كل كود ثاني بالمشروع استخدم `BranchContext::current()`
   ولم يفترض الفرع بنفسه، فيتحدّث سلوكه تلقائياً بمجرد تعديل هذا الملف الواحد.

5. **مخزون/سعر مستقل لكل فرع (اختياري):** استخدم جدول `branch_product` الجاهز أصلاً بدل تكرار
   المنتج، وحدّث شاشة المنتج بالأدمن لتعرض تبويب "المخزون حسب الفرع".
6. **فلترة الطلبات بلوحة التحكم حسب الفرع** + إضافة عمود/فلتر "الفرع" بجدول الطلبات.
7. أضف صلاحية `Branches` بـ `PermissionSeeder` الحالي عندك:
   ```php
   'Branches',
   ```

---

## 4) القاعدة الذهبية أثناء التطوير المستقبلي

أي كود جديد يحتاج يعرف "أي فرع؟" يجب أن يستدعي:
```php
App\Services\Branches\BranchContext::current()
```
ولا يفترض/يكتب فرع مباشرة بالكود. هذا هو ما يخلي التوسع لاحقاً بسيط - نقطة تغيير واحدة بدل
البحث بكل الكونترولرز عن كل مكان بيفترض "متجر واحد".
